# TINY TITANS

Original Roblox Zelda-style action-adventure designed for solo play, co-op with friends and replayability.

## Current product direction

Tiny Titans is an original adventure built around exploration, traversal, combat, environmental puzzles, tools, equipment, quests, secrets, dungeons and memorable bosses. Zelda is a gameplay reference, not an IP template.

The player uses their **standard Roblox avatar**. The old small-creature, Biomass, growth, form, ability and per-life discovery prototype has been retired; it is not part of the active runtime or current gameplay contract.

Solo and co-op are first-class. Every essential progression step must have a solo solution. Co-op should add coordination and shared stories rather than simply increasing enemy health. The long-term target is a highly replayable, polished Roblox adventure with fair monetization and meaningful reasons to return.

## Project layout

- `src/ReplicatedStorage/Shared`: pure life, reset and respawn rules.
- `src/ServerScriptService`: server-authoritative lifecycle and respawn services.
- `src/StarterPlayer/StarterPlayerScripts`: client bootstrap and life recap presentation.
- `src/Workspace`: declarative Roblox place assets managed by Rojo.
- `tools/habitat`: Habitat generator and offline geometry validator.
- `tests`: pure Luau tests runnable with Lune.

## Runtime architecture

### Server

`Bootstrap.server.lua` is the composition root. It initializes:

1. `LifeService` — sole authority for character life state and life IDs.
2. `ResetService` — exactly-once reset orchestration for each ended life; its reset payload is intentionally empty until a concrete per-life adventure system exists.
3. `RespawnService` — controlled first spawn, player-requested respawn, spawn-operation sequencing and life recap delivery.

`Players.CharacterAutoLoads = false` is set before service initialization. The server controls the first spawn. After a life ends, the player uses the recap's **BEGIN NEW LIFE** action; there is no timed automatic respawn.

### Client

`ClientBootstrap.client.lua` initializes only `LifeRecapController`. The standard Roblox avatar and its built-in character animation are the active presentation. The client sends no life ID, duration or gameplay state when requesting a new life.

### Lifecycle invariants

- Life state is owned by `LifeService`; no second service independently detects death.
- Reset tracking is per player and per life ID. Duplicate events cannot apply a reset twice.
- If a new life is observed before the previous `LifeEnded` handler runs, `LifeBegan` is the safety net that records the missed reset.
- `RespawnService` permits at most one in-flight `LoadCharacter` operation per player. A life beginning does not release that operation's lock; only its own completion does.
- A new life cannot begin until `ResetService.IsResetDone` confirms the previous life was recorded.
- The recap contains the server-derived life ID and duration only. It is replayed after the client-ready handshake and ignored after a newer life begins.

## First Habitat greybox

The existing Habitat remains a **legacy greybox**, not an approved first-region design. Batch 2 removes the old gameplay markers while preserving the traversable environment geometry.

| Model | Parts retained |
|---|---:|
| Terrain | 9 |
| Nest | 17 |
| Meadow (including north clearing) | 90 |
| RockGarden | 28 |
| GiantRoots | 29 |
| Secret | 26 |
| **Total** | **199** |

The cleanup removes exactly 24 old pickup markers and 6 old discovery trigger volumes. The remaining 199 parts retain their original names and geometry data. Spawn pads, landmarks, boundary walls, route waypoints, the Tank nook alcove, the reserved glider-span tag, and the 10-stud Leaf Platform gap remain in place.

The `.model.json` files are generated by `tools/habitat/generate_habitat.py`; do not hand-edit generated geometry. Run:

```powershell
python tools/habitat/generate_habitat.py
python tools/habitat/validate_habitat.py
```

The validator checks structure, part budget, tags, spawn pads, walking reachability and return paths, route widths, elevated and secret areas, the reserved traversal geometry, landmarks, ramp slopes and open-space constraints. It is an offline geometry model, not proof of Roblox collision, camera readability, avatar traversal or fun.

## Tests and build

Run the pure Luau suites from the repository root:

```powershell
lune run tests/Life.test.lua
lune run tests/LifeReset.test.lua
lune run tests/Respawn.test.lua
lune run tests/Lifecycle.test.lua
```

Build the place with:

```powershell
rojo build default.project.json -o build.rbxlx
```

GitHub CI runs all `tests/*.test.lua` files, the offline Habitat validator and the Rojo build. A green CI run verifies those automated checks only; it does not prove Roblox Studio behavior or player enjoyment.
